# CI 파이프라인 설계 검토 사항

| 번호 | 결정 내용 | 결정 이유 |
| --- | --- | --- |
| 1 | 실행 트리거는 `pull_request`와 `main` 브랜치 대상 `push`로 설정한다. | Pull Request 단계에서 변경 사항을 검증하고, `main` 병합 후에도 최종 상태가 깨지지 않았는지 확인할 수 있다. |
| 2 | 실행 환경은 `ubuntu-latest`를 사용한다. | Node.js 서버 테스트를 실행하기에 충분하고, GitHub-hosted runner 중 일반적으로 빠르고 호환성이 좋다. |
| 3 | Node.js 버전은 `24`로 고정한다. | README에 개발 및 검증에 사용한 버전이 Node.js v24.11.1로 명시되어 있어 로컬 검증 환경과 CI 환경의 차이를 줄일 수 있다. |
| 4 | npm 버전은 별도로 고정하지 않는다. | `package-lock.json`과 `npm ci`를 사용하면 의존성 재현성을 확보할 수 있으므로, 현재 CI에서는 npm 자체 버전을 별도 관리할 필요가 낮다. |
| 5 | 의존성 설치 명령은 `npm ci`를 사용한다. | `package-lock.json`을 기준으로 깨끗하고 재현 가능한 설치를 수행하므로 CI 환경에 적합하다. |
| 6 | 테스트 명령은 `npm test`를 사용한다. | `package.json`의 테스트 스크립트가 `node --test tests/*.test.js`로 정의되어 있고, README도 동일한 명령으로 테스트 실행을 안내한다. |
| 7 | 첫 CI에는 PostgreSQL 서비스를 띄우지 않는다. | README에 따르면 현재 자동 테스트는 빠른 재현성을 위해 인메모리 가짜 DB 어댑터로 API 흐름을 검증하므로, 기본 CI에 실제 PostgreSQL이 필요하지 않다. |
| 8 | 마이그레이션과 시드 검증은 초기 CI 범위에서 제외한다. | 현재 핵심 검증 목표는 API 테스트 통과이며, 실제 PostgreSQL 기반 `npm run migrate`, `npm run seed` 검증은 별도 확장 job으로 분리하는 편이 CI 속도와 책임 분리에 유리하다. |
| 9 | 정적 프론트엔드 빌드 단계는 추가하지 않는다. | 프론트엔드는 HTML, CSS, Vanilla JavaScript로 구현되어 별도 빌드 도구나 SPA 번들링 과정이 없다. |
| 10 | npm 의존성 캐시를 활성화한다. | `actions/setup-node`의 `cache: npm`을 사용하면 의존성 다운로드 시간을 줄일 수 있다. |
| 11 | 캐시 기준 파일은 `package-lock.json`으로 지정한다. | lockfile 변경 여부를 기준으로 npm 캐시를 갱신하면 의존성 변경과 캐시 무효화 기준이 일치한다. |
| 12 | 워크플로 권한은 `contents: read`로 제한한다. | CI는 저장소 체크아웃과 테스트 실행만 수행하므로 쓰기 권한이 필요하지 않다. |
| 13 | 같은 브랜치에서 새 실행이 시작되면 이전 실행을 취소한다. | `concurrency`와 `cancel-in-progress: true`를 사용하면 오래된 커밋에 대한 불필요한 CI 실행을 줄일 수 있다. |
| 14 | 기본 job 이름은 `test`로 둔다. | 현재 CI의 핵심 책임이 테스트 실행이므로 job 목적을 간단하고 명확하게 표현할 수 있다. |
| 15 | 배포 단계는 CI에 포함하지 않는다. | 현재 요청 범위는 품질 검증 파이프라인 구축이며, 배포는 별도 권한과 환경 변수가 필요하므로 독립된 CD 워크플로로 분리하는 것이 적절하다. |
| 16 | 향후 PostgreSQL 검증이 필요하면 별도 job으로 추가한다. | 실제 DB 마이그레이션, 시드, 동시성 검증은 가치가 있지만 실행 시간이 늘 수 있으므로 기본 테스트 job과 분리해 관리하는 것이 좋다. |
